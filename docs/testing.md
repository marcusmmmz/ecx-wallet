# Testing

`pnpm test` runs everything: the Rust tests, then a full build, then the e2e suite in headless Brave and Firefox. This page explains what the suite runs against and how to write a test.

## Two kinds of test

- **Rust tests ("Seam 2")**, in `core/*/tests/`: each module's keys, decoding, signing and building, against known vectors. `pnpm --filter @ecx/core test`.
- **e2e tests ("Seam 1")**, in `e2e/tests/`: the built extension in real browsers, plus node tests of whatever needs no browser (the wallet's TypeScript and the shipped `.wasm` against stub servers). `pnpm --filter @ecx/e2e test` after `pnpm build && pnpm build:e2e`.

Useful switches:

- `E2E_BROWSERS=brave pnpm test`: one browser only (the default is `brave,firefox`).
- `HEADFUL=1`: watch the browser.
- `node e2e/screenshots.mjs <out dir> [light|dark]`: screenshot every screen in Brave, after `pnpm build && pnpm build:e2e`.

**Fixture PSETs** (`e2e/fixtures/elements-psets.json`) are generated by `core/elements/tests/fixtures.rs`: `UPDATE_FIXTURES=1 cargo test -p ecx-elements --test fixtures`.

## The e2e build

The shipped build reads public explorers, which tests can't control. So `e2e/scripts/build.mjs` (`pnpm build:e2e`) builds the extension again from the same sources, with one change: each Chain Entry's betanet `sidechainServer` points at a local Esplora stub.

| Chain | Stub URL | Constant |
|---|---|---|
| eCash | `http://127.0.0.1:24000` | `E2E_L1_SERVER` |
| Slot 24 | `http://127.0.0.1:24024` | `E2E_SIDECHAIN_SERVER` |
| Slot 99 (Flush) | `http://127.0.0.1:24046` (Server API `flush`) | `E2E_FLUSH_SERVER` |

- Chain Entries are compiled into their modules (`core/<module>/build.rs` reads `$ECX_L1_CHAIN_ENTRY` / `$ECX_ELEMENTS_CHAIN_ENTRY` / `$ECX_FLUSH_CHAIN_ENTRY`), so `l1.wasm`, `elements.wasm` and `flush.wasm` are rebuilt, in their own cargo target dir (`core/target/e2e`). The output is in `e2e/dist/extension/{chromium,firefox}`.
- `build-output.test` checks that the two builds differ only there: every other file is byte-identical, the manifest differs only in the servers' origins, and each module's `declare()` and `chainEntry()` differ only in betanet's server.
- Browser tests run on the e2e build (`launchWallet`'s default), so none reaches a public explorer. Only `extension-loads.test` loads the shipped build (`{ build: "shipped" }`), and it opens only onboarding pages.

## Try the e2e build by hand

1. `pnpm build && pnpm build:e2e`
2. Load `e2e/dist/extension/chromium` as an unpacked extension.
3. `pnpm --filter @ecx/stub-server start`: the eCash and Slot 24 Esplora stubs, answering for the wallet "abandon … about", and an empty Flush stub (Slot 99) so turning Flush on reads a chain. Import that mnemonic.

## Writing e2e tests

### The harness (`e2e/harness.mjs`)

**Browsers and the wallet:**

- `launchWallet(name, { build, profile })`: launches Brave or Firefox with the extension. `build` is `"e2e"` (the default) or `"shipped"`. `profile` reuses a profile dir, to restart the browser on it. Also `launchBrave()` / `launchFirefox()`.
- `setUpWallet(session)`: imports "abandon … about" (`ABANDON`), no passphrase, and leaves the wallet unlocked.
- `openWalletPage(session, "#/grants")`: opens a wallet screen and waits for `[data-screen-ready]`.
- `relock(session)`: locks and unlocks from home. The wallet forgets its session cache, as on any lock, so use it in tests that change a server's chain.
- `homeSettled(page)`: waits until every card on home has its fresh balance. Close a home page only after it: a reply to a closed page makes Firefox log an error.

**A session** (what `launchWallet` returns) has:

- `waitForApprovalWindow()` and `approvalWindows()`;
- `openPage(path)`: a wallet page, e.g. `index.html#/import`. Wait for an element on it before use, since Firefox never reports `moz-extension` loads as finished;
- `extensionErrors()`: `{ manifestErrors, installWarnings, runtimeErrors }`;
- `stopBackground()`: stops the service worker or event page.

**Stub servers:**

- `serveEsplora(config)`: the Esplora stub where the e2e build's Chain Entry names Slot 24's server (`:24024`). Its config is read on every request, so a test can change it.
- `serveFlushEsplora(config)`: the same for Flush's (`:24046`), in Flush mode: it answers as Flush's explorer does (`/flush/blocks` finality from `config.finality`, `?after_txid=` paging, JSON errors; see `stub-server/src/esplora.mjs`).
- `serveL1Esplora(config)`: the same for eCash's (`:24000`). It indexes the raw transactions in `config.txs` as Esplora would and accepts broadcasts. `@ecx/stub-server/bitcoin-tx` makes and parses them.
- `serveSidechainServer(config)`: the Standard Sidechain API stub, on a free port.

The Esplora stubs listen on fixed ports, so only one test file can use each at a time (the suite runs files one by one).

**Sidechain Apps:**

- `serveTestApp()` and `openTestApp(session, app, host)`. Each `<name>.localhost` host is its own origin, and Grants are per origin.
- The test app (`e2e/test-app/`) exposes `window.testApp.request(method, params)`, which returns `{ result }` or `{ error: { code, message } }`.

**Node tests:** `importWallet()` gives the `wallet/` package bundled for node.

### Rules

- Puppeteer must never attach to the extension's service worker (`targetFilter` in the harness). To restart the worker, use `session.stopBackground()`. On Brave that's CDP `ServiceWorker.stopWorker`, over an extension page's session.
- Firefox's extension UUID is pinned, so its pages have a known URL.

## Firefox

Every e2e test runs on both browsers. On Firefox the background is a non-persistent event page, and the harness differs from Brave's in three places:

- **`extensionErrors()`:** Firefox has no extension error console API. So the harness evaluates in the browser's chrome context over BiDi (`-remote-allow-system-access`). It reads the add-on's manifest errors and warnings (`Extension.errors` / `.warnings`), and every error the browser console records from a `moz-extension://` source: uncaught exceptions and CSP violations. `extension-loads` installs a deliberately broken build to show these checks aren't vacuous.
- **`stopBackground()`** calls `Extension.terminateBackground()`, the call Firefox's idle timeout makes to suspend the event page.
- **Browser restart:** Firefox drops a temporary add-on, and its storage, when it closes. A permanent install needs a signed add-on, which release Firefox won't skip. So the harness sets `extensions.webextensions.keepStorageOnUninstall` and `keepUuidOnUninstall`, and reinstalls the add-on on relaunch. The restart test still checks what matters: `storage.local` (the encrypted vault) persists, `storage.session` (unlock state) doesn't, and the wallet comes back locked. The add-on surviving the restart is simulated, not tested: check it by hand on a signed or Developer Edition install.

## Build gates and MV3 fixes

**Gates:**

- `core/scripts/build.mjs` fails unless every `.wasm` imports nothing but memory.
- `extension/scripts/build.mjs` stages each `.wasm` once, so both browser builds ship identical bytes. It fails if any shipped script contains `eval(` or `new Function(`.

**MV3 fixes to SvelteKit's output:**

- `app/scripts/mv3-postbuild.mjs` moves SvelteKit's inline bootstrap `<script>` into a file. MV3 extension pages can't run inline scripts, and the CSP stays `script-src 'self' 'wasm-unsafe-eval'`.
- `kit.appDir` is `kit`, not `_app`: Chrome rejects extension paths starting with `_`.
