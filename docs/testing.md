# Testing

`pnpm test` runs everything: the Rust tests, then a full build, then the e2e suite in headless Brave and Firefox. This page explains what the suite runs against and how to write a test.

## Two kinds of test

- **Rust tests ("Seam 2")**, in `core/*/tests/`: each module's keys, decoding, signing and building, against known vectors. `pnpm --filter @ecx/core test`.
- **e2e tests ("Seam 1")**, in `e2e/tests/`: the built extension and web app in real browsers, plus node tests of whatever needs no browser (the wallet's TypeScript and the shipped `.wasm` against stub servers). `pnpm --filter @ecx/e2e test` after `pnpm build && pnpm build:e2e && pnpm build:e2e:web`.

Useful switches:

- `pnpm test:quick vault chains`: build, then run only the named files (`e2e/tests/<name>.test.mjs`) in Brave. Use it while working; run the full `pnpm test` before a push or merge.
- `E2E_BROWSERS=brave pnpm test`: one browser only (the default is `brave,firefox`).
- `HEADFUL=1`: watch the browser.
- `node e2e/screenshots.mjs <out dir> [light|dark]`: screenshot every screen in Brave, after `pnpm build && pnpm build:e2e`.

**Fixture PSETs** (`e2e/fixtures/elements-psets.json`) are generated by `core/elements/tests/fixtures.rs`: `UPDATE_FIXTURES=1 cargo test -p ecx-elements --test fixtures`. Flush's (`e2e/fixtures/flush-psbts.json`) come from `core/flush/tests/fixtures.rs` the same way (`-p ecx-flush`).

## The e2e build

The shipped build is mainnet's and reads public explorers, which tests can't control. So `e2e/scripts/build.mjs` (`pnpm build:e2e`) builds the extension again from the same sources for betanet (`E2E_NETWORK`, `$ECX_NETWORK`; ADR 0019), which every fixture is of, with each Chain Entry's betanet `sidechainServer` pointed at a local Esplora stub. The e2e test runs set `ECX_NETWORK=betanet` too (`@ecx/e2e`'s `test` script, `pnpm test:quick`).

| Chain | Stub URL | Constant |
|---|---|---|
| eCash | `http://127.0.0.1:24000` | `E2E_L1_SERVER` |
| Slot 24 | `http://127.0.0.1:24024` | `E2E_SIDECHAIN_SERVER` |
| Slot 99 (Flush) | `http://127.0.0.1:24046` (Server API `flush`) | `E2E_FLUSH_SERVER` |

- Chain Entries are compiled into their modules (`core/<module>/build.rs` reads `$ECX_L1_CHAIN_ENTRY` / `$ECX_ELEMENTS_CHAIN_ENTRY` / `$ECX_FLUSH_CHAIN_ENTRY`), so `l1.wasm`, `elements.wasm` and `flush.wasm` are rebuilt, in their own cargo target dir (`core/target/e2e`). The output is in `e2e/dist/extension/{chromium,firefox}`.
- `build-output.test` checks that the two builds differ only in their network and servers: the e2e build adds `elements.wasm` (Elements+ has no mainnet), every other file is byte-identical but for the background's module map, the manifest differs only in the servers' origins, each module serves its build's network, and its `chainEntry()` differs only in betanet's server.
- Tests that load a module directly (`core-modules.test`, `flush.test`…) load the e2e build's, which is betanet's. `core-modules.test` also checks that the shipped modules serve mainnet.
- Browser tests run on the e2e build (`launchWallet`'s default), so none reaches a public explorer. Only `extension-loads.test` loads the shipped build (`{ build: "shipped" }`), and it opens only onboarding pages.

### The web e2e build

`pnpm build:e2e:web` runs after `pnpm build:e2e` and reuses its stub-backed core modules. It builds the web app into `e2e/dist/web`, leaving `app/build-web` for the shipped web build. `ECX_CORE_DIST`, `ECX_CHAIN_ENTRIES` and `ECX_APP_WEB_DIST` select the WASM, the Chain Entries used to derive CSP origins, and the output directory. Slot 24 stays excluded; the web build contains L1 and Flush. The Esplora stubs send no CORS headers, like the real Elements explorer, unless a test passes `cors: true` in their config; the web tests do, since their pages can't use `host_permissions`. Web tests navigate the way in-app links do: assigning `location.hash` would bypass SvelteKit's router and reload the page, ending the Worker and its unlocked session.

`web-wallet.test.mjs` and `web-provider.test.mjs` are included by the suite's `tests/*.test.mjs` glob, and `pnpm test` builds their web output before running the suite (`pnpm test:quick` does for either name). To run just web coverage:

```sh
pnpm build && pnpm build:e2e && pnpm build:e2e:web
node --test --test-concurrency=1 --test-timeout=120000 e2e/tests/web-*.test.mjs
```

The tests create a vault, lock/unlock it, and reload to check that IndexedDB retains the vault while the Worker's memory-only unlock state is lost. They check the Chains and Send lists exclude Slot 24 and home has no pin control. Send uses Flush (Slot 99), as in `flush-wallet.test.mjs`: L1's standalone Send is not implemented. The Send form approves in place. To also exercise `#/approve/{id}`, the test observes the page's real Worker and sends an unhosted `send.start` through its existing transport, using negative request ids to avoid collisions. Approving broadcasts a transaction; rejecting returns error 4001 without a broadcast; both return to the previous Chains route in the same page. This transport driver adds no production API and is not a web Provider.

`web-provider.test.mjs` drives the web Provider (#85). It imports the wallet on the web origin (`127.0.0.1`), then opens the test app on `webapp.localhost`, a different site, with `discover({ webWallet })`. The first request comes from a button the test app arms (`testApp.arm`) and the test clicks, because `window.open` needs a click. The popup is found with `waitForTarget` on its URL. The test covers connect (approval shows the browser's origin, not the one in params), an unlock in the popup, a rejected wider Grant, `grantChanged` on `disconnect`, the app reloading with the popup open (same window, no unlock), the popup reloading during an approval (4900), and 4900 when the popup closes. A further test drives the demo app (`demo/`, bundled the way its build does, on `demo.localhost`), which imports `client.js` cross-origin from the served web build (so the `/client.js` CORS rule in `_headers` is exercised; `serveWebWallet` applies per-path rules on top of `/*`), with `?wallet=` and `?slot=99`: Connect, approve and unlock in the popup, the address shown, Disconnect. Two tests cover the Apps view (#91). In the first, the wallet frames the demo (served with `frame-ancestors` for the wallet), and Connect is refused, then approved and unlocked in the overlay, with no popup. A mark set in the frame shows it never reloaded. In the second, the demo sends its frame to a plain page that allows framing but loads no client, so the bar forgets the origin and says "Not connected". A page with `frame-ancestors 'none'` gets the same notice. The tests reach the frame with `page.waitForFrame`. `web-host.test.mjs` covers the same boundary without a browser: `serveOpener`'s origin checks, `hello` and the cross-tab Grant relay (with an in-memory `BroadcastChannel`), and the Worker's `appRequest` envelope, its spend locks, and a `slot` that can't be converted.

Each normal flow checks the navigation response's CSP header and collects page errors, console errors and `securitypolicyviolation` events. A separate test deliberately inserts an inline script and checks CSP blocks it, so enforcement is not inferred just from the header. Worker requests to the stubs must also pass the CSP sent on the Worker script. Browser execution is required to verify these checks; syntax and builds alone do not verify navigation timing, console forwarding or browser CSP support.

## Try the e2e build by hand

1. `pnpm build && pnpm build:e2e`
2. Load `e2e/dist/extension/chromium` as an unpacked extension.
3. `pnpm --filter @ecx/stub-server start`: the eCash and Slot 24 Esplora stubs, answering for the wallet "abandon … about", and an empty Flush stub (Slot 99) so turning Flush on reads a chain. Import that mnemonic.

## Writing e2e tests

### The harness (`e2e/harness.mjs`)

**Browsers and the wallet:**

- `launchWallet(name, { build, profile })`: launches Brave or Firefox with the extension. `build` is `"e2e"` (the default) or `"shipped"`. `profile` reuses a profile dir, to restart the browser on it. Also `launchBrave()` / `launchFirefox()`.
- `setUpWallet(session)`: imports "abandon … about" (`ABANDON`), no passphrase, and leaves the wallet unlocked.
- `openWalletPage(session, "#/grants")`: opens a wallet screen and waits for `[data-screen-ready]`.
- `relock(session)`: locks and unlocks from home. The wallet forgets its session cache, as on any lock, so use it in tests that change a server's chain.
- `homeSettled(page)`: waits until every card on home has its fresh balance. Close a home page only after it: a reply to a closed page makes Firefox log an error.
- `waitForFunction(page, fn, { timeout }, ...args)`: use it instead of `page.waitForFunction`, which on Firefox 159 fails for good if the page is still navigating. It polls `page.evaluate`, so `fn` returns a boolean or plain data, not an element.

**A session** (what `launchWallet` returns) has:

- `waitForApprovalWindow()` and `approvalWindows()`;
- `openPage(path)`: a wallet page, e.g. `index.html#/import`. Wait for an element on it before use, since Firefox never reports `moz-extension` loads as finished;
- `extensionErrors()`: `{ manifestErrors, installWarnings, runtimeErrors }`;
- `stopBackground()`: stops the service worker or event page.

**Web pages:**

- `serveWebWallet()`: serves `e2e/dist/web` on a free loopback port, applying the generated `_headers` global rule to every response, including JavaScript and WASM. It rejects unsupported header-file syntax. Returns `{ url, headers, close }`.
- `launchWebWallet(name)`: launches the same Brave or Firefox with no extension installed. Returns `{ browser, close }`. Keep web flows in the same page: every new page or reload creates a new Worker with a locked session.

**Stub servers:**

- `serveEsplora(config)`: the Esplora stub where the e2e build's Chain Entry names Slot 24's server (`:24024`). Its config is read on every request, so a test can change it.
- `serveFlushEsplora(config)`: the same for Flush's (`:24046`), in Flush mode: it answers as Flush's explorer does (`/flush/blocks` finality from `config.finality`, `?after_txid=` paging, JSON errors; see `stub-server/src/esplora.mjs`).
- `serveL1Esplora(config)`: the same for eCash's (`:24000`). It indexes the raw transactions in `config.txs` as Esplora would and accepts broadcasts. `@ecx/stub-server/bitcoin-tx` makes and parses them.
- `serveSidechainServer(config)`: the Standard Sidechain API stub, on a free port.

The Esplora stubs listen on fixed ports, so only one test file can use each at a time (the suite runs files one by one).

**Sidechain Apps:**

- `serveTestApp()` and `openTestApp(session, app, host)`. Each `<name>.localhost` host is its own origin, and Grants are per origin.
- The test app (`e2e/test-app/`) exposes `window.testApp.request(method, params)`, which returns `{ result }` or `{ error: { code, message } }`.

**Node tests:** `importWallet()` gives the `wallet/` package bundled for node.

### Rules

- Puppeteer must never attach to the extension's service worker (`targetFilter` in the harness). To restart the worker, use `session.stopBackground()`. On Brave that's CDP `ServiceWorker.stopWorker`, over an extension page's session.
- Firefox's extension UUID is pinned, so its pages have a known URL.

## Firefox

Every e2e test runs on both browsers. On Firefox the background is a non-persistent event page, and the harness differs from Brave's in three places:

- **`extensionErrors()`:** Firefox has no extension error console API. So the harness evaluates in the browser's chrome context over BiDi (`-remote-allow-system-access`). It reads the add-on's manifest errors and warnings (`Extension.errors` / `.warnings`), and every error the browser console records from a `moz-extension://` source: uncaught exceptions and CSP violations. `extension-loads` installs a deliberately broken build to show these checks aren't vacuous.
- **`stopBackground()`** calls `Extension.terminateBackground()`, the call Firefox's idle timeout makes to suspend the event page.
- **Browser restart:** Firefox drops a temporary add-on, and its storage, when it closes. A permanent install needs a signed add-on, which release Firefox won't skip. So the harness sets `extensions.webextensions.keepStorageOnUninstall` and `keepUuidOnUninstall`, and reinstalls the add-on on relaunch. The restart test still checks what matters: `storage.local` (the encrypted vault) persists, `storage.session` (unlock state) doesn't, and the wallet comes back locked. The add-on surviving the restart is simulated, not tested: check it by hand on a signed or Developer Edition install.

## Build gates and MV3 fixes

**Gates:**

- `core/scripts/build.mjs` fails unless every `.wasm` imports nothing but memory.
- `extension/scripts/build.mjs` stages each `.wasm` once, so both browser builds ship identical bytes. It fails if any shipped script contains `eval(` or `new Function(`.

**MV3 fixes to SvelteKit's output:**

- `app/scripts/mv3-postbuild.mjs` moves SvelteKit's inline bootstrap `<script>` into a file. MV3 extension pages can't run inline scripts, and the CSP stays `script-src 'self' 'wasm-unsafe-eval'`.
- `kit.appDir` is `kit`, not `_app`: Chrome rejects extension paths starting with `_`.
